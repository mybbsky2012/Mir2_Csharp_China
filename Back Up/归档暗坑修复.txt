改了什么
① 好友 —— 堵死坏库
CharacterInfo.Save() 里那行 if (Friends[i].Info == null) continue; 直接删掉了。

关键发现：FriendInfo.Save 只写 Index / Blocked / Memo，根本不碰 Info，那个跳过纯属多余。照写之后：

数量与条目天然一致 → 不再错位
悬空好友原样留在档里 → 角色以后 @RESTOREPLAYER 恢复（Index 不变）时，好友关系自动接回，不用重新加
顺手给 Memo 加了 ?? string.Empty（null 会让 BinaryWriter 写 -1，读回来 ReadString 抛 IOException，同样能毁掉整个库）。

② 结婚 / 师徒 —— 不再崩，并且自动解除
登录时的三个必炸点全部补上，而且不是简单跳过：

GetRelationship()：配偶查不到 → 自动解除婚姻、摘掉左戒指的 WeddingRing、发系统提示、写日志
GetMentor()：师父查不到 → 自动解除师徒、清 MentorExp（日志里记下未结算的经验数）
MentorBreak()：对方查不到 → 清零后直接返回，不再往下取 .Name
为什么选择“自动解除”而不是“保留不管”：离婚流程要求双方面对面，被归档的角色永远上不了线，保留的话玩家会永久卡在“已结婚”状态——既不能再婚，也离不了。归档文件里仍然保留着原来的 Married 值，真要恢复可以人工补。

另外把剩下 8 处未判空的调用点也扫了一遍：@配偶 聊天、换图通知、传送、心心相映/衣钵相传加成、NPC 离婚、怪物结算师徒伤害、技能熟练度加成。其中 HumanObject:8703 还顺带发现一个原有的 bug——player.CurrentMap 前面没有判 player != null，对方只是离线就会崩。

③ 停服时不存档
CleanUp() 的婚姻分支补了判空。这个比看起来严重：它在 StopEnvir 里跑，抛异常会跳过紧随其后的 SaveAccounts() —— 表现是关服时整个服没存盘。同一段的师徒分支本来就有判空，只有婚姻漏了。

④ 坏档兜底 —— 换了思路
原计划“单角色 try/catch 跳过坏档”技术上不成立：账号库是无长度前缀的顺序流，一个角色读歪了，流位置就已经错位，后面只会继续读到垃圾，try/catch 跳过这一条并不能让下一条回到正轨。

所以改成真正有效的两层：

保留上一版：SaveAccounts / EndSaveAccounts 原来把 Account.db.o 直接删掉，现在先复制成 .bak 再删
读坏自动回退：LoadAccounts 拆成“入口 + 核心”，读失败时把坏档另存为 .corrupt-时间戳（留证据），用 .bak 覆盖后重读一次；只重试一次，还不行就抛给人工处理

改了什么
Server/MirDatabase/MailInfo.cs

Send() 从 void 改成 bool。收件人查不到时不再继续调用 Mail.Add：

csharp

if (RecipientInfo == null)
{
    MessageQueue.Instance.Enqueue(
        $"邮件投递失败 #{MailID}（{Sender ?? "(无)"} → 角色ID {RecipientIndex}）：" +
        $"收件人已不在角色列表（可能已归档/删除），未投出 金币 {Gold}、物品 {Items.Count} 件");
    return false;
}
返回 false 这个设计是有用的：原来的 void 让调用方无从判断，现在至少能区分“投出去了”和“人没了”。现有 8 个调用点写成 mail.Send(); 丢弃返回值，照样编译，行为不变。

Save() 顺手补了两处 null 防御：Sender 和 Message 都加了 ?? string.Empty。这是同一类问题：BinaryWriter.Write((string)null) 会写 -1，读回来 ReadString 直接抛 IOException，整个账号库都读不完。而 new MailInfo(int) 这个构造根本不初始化 Sender，只要有一处忘了赋值，存档就会坏。

为什么值得修
这 8 个调用点中，有三个位于主循环或对象线程上：

拍卖结算给买家（CurrentBuyerInfo）
装备租赁到期退给物主（owner）
交易退款、仓库密码错误补偿（Envir.MailCharacter）
这些都是“东西已经不在玩家身上了，只能靠邮件送回去”的场景。收件人正好被归档时，原来会直接空引用，导致 Envir 主循环重启、全服掉线；现在只是记一条日志，写明多少金币、几件东西没投出去，方便你手工补。

玩家之间寄信那条 SendMail(name, ...) 上游已经用 GetCharacterInfo(name) 判断过，查不到会提示“找不到玩家”，所以实际只可能被极小概率的竞态触发。
