# 微端与大分辨率 使用说明

本次改动解决三件事：**客户端能上大分辨率**、**客户端可以做成微端（按需下载资源）**、**资源服务能扛住上百人同时在线**。两端代码都改好了，已编译、部署并做过实测。

> 微端的加载策略是「**边玩边加载**」：客户端启动阶段**一个资源都不下载**，  
> 缺失的资源只在玩家真正用到它的那一刻才向服务端取。详见 **§2.2**。
>
> 多人同时在线时的承载能力与压测数据，见 **§2.9**。

---

## 一、大分辨率支持

### 1.1 之前为什么上不去

不是客户端的问题，是**服务端把你锁死了**。

`Configs\Setup.ini` 里有一项：

```ini
[Permission]
MaxResolution=1024
```

服务端在「进入游戏」这一步会把 `AllowedResolution` 下发给客户端，而客户端 `SelectScene` 里有一行：

```csharp
if (p.Resolution < Settings.Resolution || Settings.Resolution == 0)
    Settings.Resolution = p.Resolution;
```

`p.Resolution` 是服务端给的**上限**。客户端哪怕选了 1920，只要超过 1024 就会被强制降回来。所以光改客户端没用。

### 1.2 改了什么

**服务端**

- `MaxResolution` 默认值 1024 → **1920**
- `Setup.ini` 里已改为 `MaxResolution=1920`

**客户端**

- 分辨率档位从 4 个增加到 **6 个**：
  | 档位        | 说明                         |
  | --------- | -------------------------- |
  | 1024×768  | 默认                         |
  | 1280×720  | 修正了原来「枚举写 720、实际用 800」的不一致 |
  | 1366×768  |                            |
  | 1600×900  | **新增**                     |
  | 1920×1080 |                            |
  | 2560×1440 | **新增**                     |
- 新增 `Resolution/ResolutionHelper.cs`：分辨率 ↔ 窗口尺寸的**唯一映射表**。  
  以前这个映射硬编码散落在 `SelectScene`、`GameScene` 三个地方，1280 那档还写错了，增删一档极容易漏改。
- 配置界面（启动器的「显示设置」）改为数据驱动，新增档位不用再改 designer 文件。
- 高分辨率档位在**窗口模式下不再受「显示器必须原生支持」的限制** —— 只要窗口不超过桌面就能选，否则 1600×900 这类档位在部分机器上会无谓地显示成灰色。

### 1.3 怎么用

1. 启动器「显示设置」里点开新分辨率，或直接改 `Mir2Config.ini` 的 `[Graphics] Resolution=1920`
2. 想再往上开（比如 2560×1440），把服务端 `Configs\Setup.ini` 的 `MaxResolution` 改成 `2560`
3. **服务端要重启**，配置才生效

### 1.4 关于大分辨率下的界面表现

游戏**视野**会随分辨率真实变大（地图绘制范围按屏幕尺寸计算，`OffSetX = ScreenWidth / 2 / CellWidth`），这点是原生支持的。

**底栏自适应（2026-10-07 已撤销）**：曾试验「整宽底栏」——把原版底栏的纯栏杆中段镜像平铺成
整宽图（`Data\PrguseEx.Lib`）垫在主界面底下。实测两侧栏杆是半透明的，游戏画面透出来显得发虚，
用户不满意，**已撤销**：`PrguseEx.Lib` 已从客户端与微端删除/改名停用，客户端代码保留但自动退回
原版「居中 1024 底栏 + 两侧端帽」表现（原版本就不支持整宽，只是居中 + 端帽装饰）。
如需重新启用：把 `PrguseEx.Lib` 放回 `Data\` 即可（存档在 WorkBuddy 工作区 `tools/PrguseEx.Lib`，
生成脚本 `tools/rebuild_prguseex.py`）。

## 二、微端（按需下载资源）

### 2.1 原理

完整客户端 **9.99 GB**，其中真正「进游戏就要用」的只有界面图库、程序文件和 DirectX 运行库。微端的做法是：

- 客户端只带**核心资源**（约 **678 MB**，是完整包的 **6.8%**）
- 其余资源（角色/怪物/NPC 图库、音效、地图，合计约 **9.3 GB**）在**真正用到那一刻**才向服务端拉取
- 拉取后存到本地，下次直接用，不会重复下载

一句话概括：**玩家是边玩边把资源补齐的，不是先等它全部下完再进游戏。**

接入的加载点（一共 6 处，覆盖全部资源类型）：

| 资源             | 加载点                             |
| -------------- | ------------------------------- |
| 图库 `.Lib`      | `MLibrary.Initialize()`         |
| 地图 `.map`      | `MapReader.Initiate()`          |
| 音效 `.wav/.mp3` | `CachedSound`、`LoopProvider`    |
| 音效索引表          | `SoundList.LoadSoundList()`     |
| 着色器 `.ps`      | `DXManager.LoadPixelsShaders()` |

### 2.2 加载策略：为什么它真的是「边玩边加载」

微端最容易踩的坑，是**在启动时把所有资源全下一遍**。这个客户端启动时会做一件事：  
把上千个图库目录逐个「登记」一遍（`Libraries.LoadGameLibraries()`）。如果登记时顺手去下载，  
那就变成「先等十几分钟下完 9.3GB 才能进游戏」—— 那就完全不是微端了。

所以下载器按「资源是不是现在就要用」分成了三种处理方式：

| 场景                                                  | 行为                                  | 玩家感受                               |
| --------------------------------------------------- | ----------------------------------- | ---------------------------------- |
| **启动批量登记**<br />`BeginBulkLoad()` ~ `EndBulkLoad()` | 只查本地文件，**一个下载请求都不发**                | 启动速度和完整客户端一样，不用等                   |
| **用到才取**（图库、音效、背景音乐）                                | 把请求丢进后台队列就立刻返回，缺的这一帧跳过不画；下完自动补上     | 第一次遇到新怪物/新装备时最多晚 0.25 秒出现，**画面不卡** |
| **缺了就没法继续**（进入地图的 `.map`、着色器、音效索引表）                 | 有限等待下载完成（地图 30s，其余 10~15s），超时走原兜底逻辑 | 进新地图时会等一小下，之后本地有缓存就不再等             |

几个细节：

- **后台队列**：默认 2 个下载线程（`Concurrency`），串行去重，同一个文件不会重复下。
- **不抢网速**：`RateLimit` 可以给每个线程限速（KB/s），默认 0 不限速。
- **清单预判**：客户端手里有服务端资源清单，清单里没有的文件**连试探请求都不发**，  
  避免对着不存在的文件狂刷 404（音效要按多个扩展名逐个找，这项收益最大）。
- **负缓存**：下载失败的文件本次运行不再重试，不会因为服务端打不通而反复卡顿。
- **原子写入**：先写 `.tmp` 再改名，断线留下的半截文件不会被当成有效资源加载。
- **游戏内提示（默认关闭）**：聊天框的「微端已启用 / 资源补齐完成」提示默认**不显示**，  
  玩家完全看不到下载过程（微端本来就是后台悄悄补资源）。排障时把 `Mir2Config.ini`  
  的 `[MicroClient] Hint` 改成 `True` 即可看到。

### 2.3 服务端配置（已配好）

`Configs\Setup.ini` 的 `[Network]` 段：

```ini
StartHTTPService=True
HTTPIPAddress=http://+:5679/
HTTPTrustedIPAddress=127.0.0.1
HttpTransport=auto
EnableResourceService=True
ResourcePath=..\20260915Client\
ResourceAllowAnyIP=True
ResourceMaxConcurrent=64
ResourceWriteTimeout=300
ResourceBufferKB=64
ResourceVerboseLog=False
```

| 项                       | 说明                                                            |
| ----------------------- | ------------------------------------------------------------- |
| `StartHTTPService`      | 「启用HTTP服务」：注册账号、改名、广播等**管理接口**的开关。关掉后这些接口一律返回 404             |
| `EnableResourceService` | 开微端资源服务（**微端下载资源必须开**）。它需要一个监听才能发资源，所以后面三个 `/res*` 接口的放行与它绑定  |
| `HTTPIPAddress`         | 监听地址。监听全部网卡写 `http://+:5679/`；**不要写 `0.0.0.0`**（详见 §2.8 坑三）   |
| `HttpTransport`         | 监听通道：`auto`（默认，http.sys 不行就自动用纯 Socket）/ `httpsys` / `socket` |
| `ResourcePath`          | 完整资源所在目录。当前指向你的完整客户端，**它就是这个服对外提供资源的「仓库」**                    |
| `ResourceAllowAnyIP`    | 允许任意 IP 请求资源（玩家客户端要下载，必须开）。管理类接口仍只允许 `HTTPTrustedIPAddress`   |
| `ResourceMaxConcurrent` | 同时传输的请求数上限（默认 64），详见 [2.9](#29-上百人同时在线扛得住吗)                   |
| `ResourceWriteTimeout`  | 单个请求最长传输秒数（默认 300），超时断开清理卡死的连接                                |
| `ResourceBufferKB`      | 流式发送的分块大小（默认 64KB）                                            |
| `ResourceVerboseLog`    | 是否逐条记录资源下发（默认 False）。高并发下开启会明显拖慢，仅供排障                         |

#### ⚠️ 「启用HTTP服务」关了，为什么 HTTP 监听还在跑？

这两个是**不同的开关**，别混：

| 开关                                        | 管什么                | 关了会怎样                 |
| ----------------------------------------- | ------------------ | --------------------- |
| `StartHTTPService`（设置窗口里叫「启用HTTP服务」）      | 注册/改名/广播这类**管理接口** | 这些接口 404；**监听本身不受影响** |
| `EnableResourceService`（设置窗口里叫「启用微端资源服务」） | 微端资源下发             | 微端下载彻底失效（玩家卡在缺资源）     |

只要 `EnableResourceService=True`，就必须有一个 HTTP 监听把资源发给玩家，所以启动日志里  
仍会看到「Http服务器 …」；**这不是 bug**。此时只放行 `/resource`、`/resindex`、`/resinfo`，  
管理接口全部停用——「关了 HTTP 服务却还能注册账号」这种情况已经不会发生。

想彻底不监听：把「启用微端资源服务」也取消勾选（`EnableResourceService=False`），  
服务端就不会再起任何 HTTP 端口。代价是玩家端微端包下不到缺失资源。  
两个开关现在都能在**服务端设置窗口 →「网络」页**直接勾选，不用再手改 ini。

服务端提供的三个接口：

| 接口                                     | 用途                            |
| -------------------------------------- | ----------------------------- |
| `GET /resource?f=Data/Monster/000.Lib` | 下载单个资源                        |
| `GET /resindex`                        | 返回全部资源清单（客户端靠它推算各图库目录该有多少个文件） |
| `GET /resinfo`                         | 查看资源服务状态，排错用                  |

### 2.4 客户端配置

客户端 `Mir2Config.ini` 末尾已加好：

```ini
[MicroClient]
Enabled=False
Host=http://127.0.0.1:5679/
Timeout=8000
Log=True
Concurrency=2
RateLimit=0
Hint=False
```

| 项             | 说明                                                                                       |
| ------------- | ---------------------------------------------------------------------------------------- |
| `Enabled`     | 默认 **False**。你自己的这台是完整客户端，不需要按需下载，保持 False 最省事（避免每次启动多拉一次资源清单）                           |
| `Host`        | 资源服务地址。给外网玩家用时，要换成服务端能被访问到的地址                                                            |
| `Timeout`     | 单文件下载超时（毫秒）。网络慢可以调大                                                                      |
| `Log`         | 写 `MicroClient.log`，下载了什么、什么失败了都记在里面，排错很有用                                               |
| `Concurrency` | 后台下载线程数，默认 2。调大补资源更快，但更占带宽                                                               |
| `RateLimit`   | 每个线程的限速（KB/s），默认 0 不限速。想「尽量不影响玩」可以设成 512                                                 |
| `Hint`        | 是否在聊天框显示「微端已启用 / 资源补齐完成」。**默认 False**，玩家看不到任何下载提示（微端本来就是后台悄悄补资源）；需要确认"到底有没有在下"时改成 `True` |

想让**别人**用微端，用下面的脚本生成一个微端客户端包即可，**不用手动改配置** ——  
包里有 `microclient.flag` 标记文件，客户端看到它会自动开启微端。

### 2.5 制作微端客户端包

```bash
python Tools/make_micro_client.py [源客户端目录] [输出目录] [资源服务地址]
```

不给参数就用默认值，直接跑即可。它会：

1. 复制程序文件、`DirectX/`、`Localization/`、`Data` 顶层的界面图库
2. 写入 `microclient.flag`（自动启用微端）
3. 生成**干净的** `Mir2Config.ini` —— 注意原客户端的账号密码不会被带出去
4. 预先建好按需目录，避免首次运行报找不到目录

### 2.6 体积效果

|              | 体积         | 占比    |
| ------------ | ---------- | ----- |
| 微端包（发出去）     | **678 MB** | 6.8%  |
| 按需下载（玩家用到才拉） | 9304 MB    | 93.2% |
| 完整客户端        | 9987 MB    | 100%  |

其中按需部分主要是：角色/怪物/装备图库 7.4 GB、地图 1.5 GB、音效 445 MB。

### 2.7 安全设计

资源服务是对外开放的，所以做了三层限制，都已实测验证：

1. **目录白名单** —— 只放行 `Data/`、`Map/`、`Sound/`、`DirectX/`、`Localization/`。  
   否则资源目录一旦指向客户端根目录，别人就能顺着接口把 `Mir2Config.ini`（内含保存的账号密码）拖走。
2. **路径穿越防护** —— `../`、`..%2F`、`..%5C`、绝对路径全部拦截，规范化后必须仍落在资源根目录内。
3. **信任 IP 机制保留** —— `/broadcast`、`/newaccount` 等管理接口仍只允许 `HTTPTrustedIPAddress`，只有 `/res*` 对任意 IP 开放。

### 2.8 对外开放：为什么把 IP 改成固定地址反而连不上

这是最容易踩的一个坑：`IPAddress` 和 `HTTPIPAddress` 看着像同一类东西，但**报错原理完全不同**。

#### 先说结论

| 想达到的效果         | `Setup.ini` 应该这样写                                                                 |
| -------------- | --------------------------------------------------------------------------------- |
| 只有本机玩（默认，最省事）  | `IPAddress=127.0.0.1`<br />`HTTPIPAddress=http://127.0.0.1:5679/`                 |
| 本机 + 局域网/外网都能玩 | `IPAddress=0.0.0.0`<br />`HTTPIPAddress=http://+:5679/`<br />`HttpTransport=auto` |

**两处都对，就一定能起来** —— 新版服务端会自动挑监听通道：  
http.sys（内核态）能用就用它，用不了（没登记、没给管理员权限）就自动改用纯 Socket，  
和游戏主端口同一套权限模型，**不需要任何管理员权限**。

**关键：不要填「具体的某个 IP」。** `0.0.0.0` 表示"监听本机所有网卡"，  
本机的 `127.0.0.1` 和对外 IP 会**同时**监听；填具体 IP 则只监听那一个地址。

**HTTPIPAddress 千万不要跟着 IPAddress 一起写 `0.0.0.0`** ——  
那是两个不同的东西，写错了报的是另一个错误码（见下面坑三）。

#### 坑一：`IPAddress` 填具体 IP → 游戏端口 7000 连不上

服务端建监听时用的是（`Envir.cs:1866`）：

```csharp
_listener = new TcpListener(IPAddress.Parse(Settings.IPAddress), Settings.Port);
```

这是**绑定到那一个网卡地址**，不是"监听全部"。所以把 `127.0.0.1` 改成 `192.168.2.234` 之后：

- **本机客户端仍然连的是 `127.0.0.1`，而服务端已经不在回环上监听了 → 本机自己也连不上**  
  （这是最常见的"改完就进不去游戏"）
- 别的机器上的客户端必须把 `Mir2Config.ini` 的 `IPAddress` 改成 `192.168.2.234` 才连得上
- 如果填的 IP **根本不在本机网卡上**（写错、或者填了公网 IP），`_listener.Start()` 会直接抛  
  `10049 在其上下文中，该请求的地址无效`，**服务端启动就失败**

实测（本机真实网卡 `192.168.2.234`）：

```
OK    bind 0.0.0.0          监听全部网卡
OK    bind 192.168.2.234    本机真实局域网 IP
OK    bind 127.0.0.1        仅回环
FAIL  bind 192.168.1.100    errno=10049 在其上下文中，该请求的地址无效
FAIL  bind 1.2.3.4          errno=10049 在其上下文中，该请求的地址无效
```

#### 坑二：`HTTPIPAddress` 填具体 IP → 需要授权（老版会直接起不来）

`HttpListener` 底层不是普通 socket，而是 Windows 的 **http.sys**。前缀必须先在系统里  
**登记（URL 保留项）** 过，否则只有两种情况能启动：

- `http://127.0.0.1:端口/` 或 `http://localhost:端口/` —— **免登记**，普通用户即可
- 其余形式（具体网卡 IP、`http://+:端口/`、`http://*:端口/`）—— 老版本**必须**满足其一：
  - 服务端以**管理员身份**运行，或
  - 预先登记过 URL 保留项

实测（非管理员会话，本机无任何 5679 的保留项）：

```
OK    http://127.0.0.1:5679/
OK    http://localhost:5679/
FAIL  http://192.168.2.234:5679/   →  拒绝访问(5)。
FAIL  http://192.168.56.1:5679/    →  拒绝访问(5)。
FAIL  http://+:5679/               →  拒绝访问(5)。
FAIL  http://*:5679/               →  拒绝访问(5)。
```

失败时被 `HttpService.cs` 的 catch 接住，只往消息队列打一句  
`Http服务器 启动失败! 错误:System.Net.HttpListenerException (5): 拒绝访问。`  
**服务端本身照常运行**，所以现象是"服务端在跑，但微端资源下载全失败"——  
很容易误判成别的问题。（新版已在这句后面补了可操作提示。）

#### 坑三：`HTTPIPAddress` 写成 `0.0.0.0` → HttpListenerException (50) 不支持该请求

```
Http服务器 启动失败! 错误:System.Net.HttpListenerException (50): 不支持该请求。
at System.Net.HttpListener.AddPrefixCore(String registeredPrefix)
at System.Net.HttpListener.AddAllPrefixes()
at System.Net.HttpListener.Start()
at Server.Library.Utils.HttpService.Listen(Object obj)
```

**同一个错误码对应同一个坑**：`IPAddress` 那行改成 `0.0.0.0` 生效了，  
就顺手把 `HTTPIPAddress` 也写成 `http://0.0.0.0:5679/`。

问题在于这两行的含义根本不同：

- `IPAddress=0.0.0.0` 是**套接字绑定地址**，"监听本机所有网卡"，合法；
- `HTTPIPAddress` 是**URL 前缀**，其中的主机名由 http.sys 解析，  
  它只认 `+`（强通配）、`*`（弱通配）、`localhost`、具体 IP / 主机名，  
  **`0.0.0.0` 不在其中**，于是直接 `ERROR_NOT_SUPPORTED (50)`。

记住两条即可：

| 想表达      | 写法                           |
| -------- | ---------------------------- |
| 监听所有网卡   | `http://+:5679/`             |
| 只监听某一个网卡 | `http://192.168.2.234:5679/` |
| 只本机能玩    | `http://127.0.0.1:5679/`     |

> 新版服务端在读到配置后会先把地址规范化：`0.0.0.0` / `*` / `any` / `::` 自动翻译成 `+`，  
> 漏写的 `http://`、漏写的端口、漏写的尾部 `/` 也都会补齐，所以这个错误码在新版里不会再出现。

#### 错误码速查

| 错误码         | 含义     | 原因                                  |
| ----------- | ------ | ----------------------------------- |
| 5           | 拒绝访问   | 非回环地址没登记 URL 保留项，也没用管理员运行           |
| 50          | 不支持该请求 | 主机名写法 http.sys 不认（最常见：写成 `0.0.0.0`） |
| 183 / 10048 | 端口被占用  | 上一个 `Server.exe` 没退干净，或别的程序抢了端口     |
| 10049       | 地址无效   | 填的 IP 不是本机网卡地址（游戏端口 7000 报这个）       |

#### 新版怎么处理：自动挑监听通道（`HttpTransport`）

为了让"改固定 IP"这件事不再依赖系统授权，新版把资源下发做成了**与通道无关**，  
业务逻辑（`/resindex`、`/resource`、越权拦截、并发闸门、流式发送）两份通道共用：

| `HttpTransport` | 行为                                    |
| --------------- | ------------------------------------- |
| `auto`（默认，推荐）   | 先试 http.sys；够不着就自动改用纯 Socket，日志里会写明原因 |
| `httpsys`       | 只用 http.sys（要管理员权限或 URL 保留项）          |
| `socket`        | 只用纯 Socket（不需要任何权限）                   |

实测（本机，非管理员，无任何 URL 保留项）：

```
配置 http://0.0.0.0:5679/      auto   →  实际监听 http://0.0.0.0:5679/   [socket]   ✅
配置 http://+:5679/            auto   →  实际监听 http://0.0.0.0:5679/   [socket]   ✅
配置 http://192.168.2.234:5679 auto   →  实际监听 http://192.168.2.234:5679/ [socket] ✅
配置 http://127.0.0.1:5679/    auto   →  实际监听 http://127.0.0.1:5679/ [httpsys]  ✅
配置 http://0.0.0.0:5679/      httpsys→  退回 http://127.0.0.1:5679/ + 醒目警告   ⚠️
```


纯 Socket 通道的效果同样经过实测（走局域网网卡 `192.168.2.234:5681`，非环回）：

```
/resindex        6701 个文件，146 KB，66 ms
Data/NPC/72.Lib  615 字节，与本地文件 MD5 一致
Data/ChrSe1l.Lib 47 MB，与本地文件 MD5 一致，401 MB/s
越权路径         Mir2Config.ini / ../Server/Server.exe → 404 invalid path
长连接           同一 TCP 连接连发 3 个请求全部 200（keep-alive）
并发压测         并发 16 → 743 MB/s；并发 64 → P95 92 ms，无串行排队
慢客户端         10 个 200KB/s 慢下载者同时在线，正常请求延迟 13ms → 8ms
```

> 换成 socket 之后，绑 `0.0.0.0` 和游戏主端口 `7000` 走的是**同一套权限模型**，  
> 所以"游戏能连、资源下不动"这种半通不通的状态基本不会再出现。

#### 正确做法：跑一次一键配置脚本

3. 询问是否登记 URL 保留项（`netsh http add urlacl url=http://+:5679/ user=Everyone`）  
   —— **现在这一步是可选的**，不登记也会自动走纯 Socket 通道
4. 打印验证结果和后续要改的配置项

手动执行等价命令：

```cmd

然后改 `Configs\Setup.ini`（**改完必须重启服务端**）：

```

服务端启动后，控制台会直接打印真正生效的地址和客户端该填什么，例如：

如果 http.sys 起不来，它还会把**每个候选地址失败的原因**逐条列出来，  
不用再去猜"为什么监听地址和配置的不一样"。

> 服务端会在两处把**内存里的旧配置**写回 `Setup.ini`：  
> 关闭「设置」窗口时（`ConfigForm_FormClosed`）、以及程序退出时（`Program.Main` 末尾的 `Settings.Save()`）。  
> 如果你在服务端运行期间手改了 ini，一关它就被覆盖回去 —— 看起来就像"改了没用"。  
> 更稳的做法是**直接在服务端的「设置」窗口里改**，改完点「保存」再重启。

**想走内核态 http.sys（性能略高）**：授权任选其一——  
`netsh http add urlacl ...` 登记一次，或 **右键 `Server.exe` → 以管理员身份运行**。

#### 还要改的：客户端和微端包

[MicroClient]

```

```

否则玩家的微端包默认指向 `127.0.0.1`，在他自己机器上永远下载失败  
（失败还会进负缓存，本次运行不再重试）。

#### 跨网段还有一层：路由器端口映射

上面解决的是"服务器自己能不能监听"。如果玩家在**外网**（不在同一个局域网），

### 2.9 上百人同时在线，扛得住吗

**改造前扛不住。** 实测数据（本机环回，磁盘缓存全命中，属于最理想条件）：

| 场景                             | 改造前                                |
| ------------------------------ | ---------------------------------- |
| 并发 1                           | 135 MB/s，平均 14 ms                  |
| 并发 128                         | 208 MB/s，平均 765 ms，P95 **1193 ms** |
| **1 个 200KB/s 的慢客户端在下 7MB 地图** | 其他人平均延迟 **1369 ms**，最慢 **33.7 秒**  |

三个原因，都在服务端：

1. **HTTP 服务是单线程串行** —— `HttpService.Listen()` 一次只取一个连接，处理完才取下一个。并发再高也只是排队，吞吐卡在约 100 个/秒上不去。
2. **同步写 socket** —— 一个外网小水管玩家下载大文件时，写操作会一直阻塞，把唯一的处理线程占死：**全服其他人的请求跟着一起停摆**。这是最致命的一条。
3. **整块读文件** —— 每次请求都用 `File.ReadAllBytes` 把整个文件读进内存，最大的图库有 47MB。

**改造后：**

| 场景                        | 改造后                           |
| ------------------------- | ----------------------------- |
| 并发 1                      | 207 MB/s，平均 9 ms              |
| 并发 16                     | 658 MB/s，平均 43 ms             |
| 并发 128                    | 601 MB/s，平均 114 ms，P95 203 ms |
| 并发 256                    | 617 MB/s，平均 91 ms，P95 144 ms  |
| **10 个 200KB/s 慢客户端同时下载** | 其他人延迟 **13 ms → 13 ms（零影响）**  |

具体改了什么：

1. **并发处理** —— `GetContext()` 取到连接后立刻交给线程池，不再等它发完才取下一个。
2. **并发闸门** —— 同时最多 64 条在传输（`ResourceMaxConcurrent`）。作用是限流、防止上百人同时读盘把磁盘打爆，**不是**排队等一个人下完。
3. **流式发送** —— 分块读、分块写，内存占用恒定为 64KB 缓冲，不再整块读进内存。
4. **传输超时** —— 客户端卡死（拔网线、断网）时 300 秒后主动断开，把闸门名额放出来（`ResourceWriteTimeout`）。
5. **清单缓存加锁 + 字节缓存** —— 上百个请求同时到达时只遍历一次目录。
6. **日志降噪** —— 原来每下发一个资源就写一条日志（消息入队 + 落盘），高并发下这本身就是瓶颈，现在默认关闭（`ResourceVerboseLog`）。
7. **客户端复用连接** —— 原来是每下载一个文件就 `new HttpClient()`，等于每个请求新建一条 TCP 连接；现在走连接池，服务端不再堆积 TIME_WAIT。

**真正的瓶颈会转移到上行带宽：**

改造后服务端吞吐已达 617 MB/s（受本机磁盘带宽限制），并发 256 时延迟仍在 150 ms 以内。也就是说**服务端的处理能力不再是瓶颈**，决定能同时服务多少人的是服务器的**上行带宽**：

- 局域网千兆（约 110 MB/s）：100 人每人补 50 个文件（约 90 MB）→ 合计约 9 GB，约 **80 秒**发完
- 家庭宽带上行 20 Mbps（约 2.5 MB/s）：同样的量需要 **1 小时**

所以玩家在外网时，请先测一下服务器的**上行**带宽 —— 它才是真正的天花板。

**可调参数**（`Configs\Setup.ini` 的 `[Network]` 段）：

| 参数                      | 默认    | 说明                                                              |
| ----------------------- | ----- | --------------------------------------------------------------- |
| `ResourceMaxConcurrent` | 64    | 同时传输数。机械硬盘不建议调太高（随机寻道会拖慢）；SSD 且带宽充足可调到 128                      |
| `ResourceWriteTimeout`  | 300   | 单个请求最长传输秒数的**下限**。实际会按文件体积自动放宽（见 [2.10](#210-大文件也能下完588mb-的图库)） |
| `ResourceBufferKB`      | 64    | 流式发送的分块大小                                                       |
| `ResourceVerboseLog`    | False | 排障时改 True，会逐条记录下发了哪个资源                                          |

### 2.10 大文件也能下完：588MB 的图库

**资源体积的跨度远超直觉。** 这个客户端里超过 30MB 的文件有 **60 个，合计约 4GB**，最大的一个：

| 文件                                  | 体积           |
| ----------------------------------- | ------------ |
| `Data/Map/WemadeMir2/Tiles.Lib`     | **588.7 MB** |
| `Data/Monster/580.Lib`              | 147.0 MB     |
| `Data/Monster/610.Lib`              | 123.4 MB     |
| `Data/Monster/637.Lib`              | 122.8 MB     |
| `Data/Map/ShandaMir2/Objects25.Lib` | 95.6 MB      |
| `Data/Effect_32bit.Lib`             | 110.0 MB     |

这会踩到一个不起眼但致命的坑：**下载超时不能用固定值**。

原来的实现用 `HttpClient.Timeout` 固定 **32 秒**，而 `HttpClient.Timeout` 在 `ResponseHeadersRead` 模式下**会一直管到响应体读完**。于是：

- 588MB 的图库，外网 2.5MB/s 的玩家需要 **约 4 分钟** → **必然在 32 秒被判失败**
- 而失败会进入负缓存，本次运行不再重试 → 玩家卡在那儿，怎么等都等不出来

**改法：超时改成「多久没收到数据」，而不是「总共用了多久」。**

- 等响应头阶段：给固定上限（30 秒起），服务器没起来时不会无限挂着
- 响应头一到：把这个总超时撤掉，接下来的时长不受限制
- 读数据阶段：每次读取单独计时（30 秒），**只要数据还在流就不算超时**

服务端也做了对应调整：`ResourceWriteTimeout` 现在是**下限**，实际会按文件体积自动放宽（按最低可接受速度 256KB/s 推算，上限 2 小时），否则外网玩家下一半会被服务端当作卡死掐断。

**验证方式**（`Tools/verify_slow_download.py`）：起一个限速 **200KB/s** 的资源服务，让真实 `Client.dll` 下载一个 **8MB** 文件 —— 正常需要约 41 秒，**远超旧的 32 秒上限**。

```
下载返回 : True
实际耗时 : 41.8 秒      ← 旧的固定超时是 32 秒，这一项就是修复的证据
落盘字节 : 8388608
PASS
```

**给外网玩家的建议**：上面的超大文件按需下载意味着「首次进入相关地图要等几十分钟」。如果玩家主要在外网，可以考虑：

- 把 `Data/Map/WemadeMir2/`、`Data/Map/ShandaMir2/` 这两个目录也预置进微端包（包体约 +1GB，但避开最大的那批文件）
- 或者干脆给外网玩家发**完整客户端包**，微端只用在局域网/内网环境

### 2.11 启动不再卡半分钟：点「开始」立刻进登录/载入界面

**现象**：服务器连不上（或正在重启）时，点「开始」要等 **30~45 秒**才出现登录界面的「正在尝试连接服务器」。

**根因（都在客户端启动路径上，且都是「为了拿不到的东西干等」）**：

| 卡点                                        | 原来                          | 说明                                                                |
| ----------------------------------------- | --------------------------- | ----------------------------------------------------------------- |
| 像素着色器 `Data/Shaders/normal.ps`、`magic.ps` | 每个阻塞等 **15 秒**              | 服务端资源目录里**根本没有**这两个文件（只有 `grayscale.ps`），等满超时也等不来；服务器一连不上就白等 30 秒 |
| 资源清单 `GetRemoteIndex`                     | 别的线程在拉时**死等 10 秒**          | `Libraries` 初始化要调用三十多次，最坏叠加成几分钟                                   |
| 阻塞等文件 `EnsureLocalFileBlocking`           | 清单没拿到时也等满 15~30 秒           | 清单没到手就**无法判断**服务端有没有这个文件，等满超时几乎不会有结果                              |
| 启动器补丁列表 `AMain.Download`                  | `HttpClient` 默认 **100 秒**超时 | 补丁服务器连不上时「开始」按钮迟迟点不了                                              |

**改法**（原则：**登录/进图界面出现之前，绝不为「拿不到的网络资源」干等**）：

- `DXManager.LoadPixelsShaders` 改为**非阻塞**：本地有就编译，没有就把请求排进后台下载队列立刻返回（着色器缺失只影响灰度/魔法滤镜的表现，`SetNormal`/`SetGrayscale`/`SetBlendMagic` 对 null 都有保护，不影响进游戏）；下次启动客户端自然就有了。
- `ResourceDownloader.GetRemoteIndex` 给「等清单」加 **2.5 秒总预算**（分 250ms 一段消耗）：服务端正常时照样能立刻拿到正确长度；连不上时最多等 2.5 秒就放行，图库数组走原有的「降级初始化 + 清单到手后重建」。
- `EnsureLocalFileBlocking` 在**清单还没拿到**时把等待收缩到 **1.5 秒**（清单到手后仍按原超时等，进地图该等还是等）。
- 启动器 `AMain.Download` 的 `HttpClient.Timeout` 收紧到 **10 秒**。

**效果**：服务器连不上时，从点「开始」到看到「正在尝试连接服务器」从 30~45 秒缩短到 **3 秒以内**；服务器正常时行为不变（清单照样在启动早期到手）。

**开始游戏 / 进地图的「LOADING 载入画面」**（`MirScenes/LoadingScreen.cs`，新建）：

**覆盖的时间段**：在选人界面点「开始游戏 / 进入游戏」的**那一瞬间**就亮起来，先盖住「游戏资源（图库）后台加载」的阶段（此时选人大厅看起来还能点，其实资源没就绪，旧版只在大厅底部显示一个小小的 Loading 动画、大载入背景不出现），资源加载完再继续盖住「进入游戏世界」的阶段，直到**新地图底板和角色对象都真正画出来**为止。全程铺：

- 全屏黑底 + 居中的**金色 MIR2 圆环标志**（`ChrSel` 第 14 帧，Index 13，800×600，与登录界面同系列；⚠️ 别用 ChrSel[17]/[18]，那两帧是近乎全黑的过渡图，实测最亮像素只有 74/255，铺出来等于没有）
- 底部居中白色文字，随阶段变化（白字黑描边）：
  - 游戏资源（图库）还在加载 → 「正在加载游戏资源 x/y...」（`Libraries.Progress / Libraries.Count` 实时刷新；资源加载阶段不设超时，后台线程一定会跑完）
  - 资源就绪、进入请求已发出 → 「正在进入游戏，请稍候...」
- 底部居中的 **「Loading...」动画**（`Prguse` 第 941~949 帧，Index 940 起 9 帧，92×20）

**为什么不能「地图一建好就撤」**：点开始之后的黑屏其实分三段，前两段都还没画面可看：

| 阶段                                            | 客户端状态                                                                                                         | 屏幕                                                          |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| ① 点开始 → 服务端回 `StartGame`                      | 还在选人场景，请求在路上                                                                                                  | 原来是选人界面硬切黑                                                  |
| ② 回包 → `MapInformation`                       | `GameScene` 刚建、`MapControl` 还没建                                                                               | 全黑                                                          |
| ③ `MapInformation` → `UserInformation` → 底板首绘 | `MapControl` 有了但 `LoadMap()` 只填了格子数据；`User == null` 时 `MapControl.CreateTexture()` 直接 return，`DrawFloor()` 没跑 | **全黑**（旧逻辑一看到 `MapControl != null` 就把载入画面撤了 → 这才是玩家看到的那段黑屏） |

所以判据是「世界真的能画了」：`MapControl != null && User != null && MapControl.FloorValid`（`FloorValid` 由 `DrawFloor()` 末尾置位，即底板真的画过一次）。

**`Armed` 机制**：`LoadingScreen.Show()` 点亮载入画面并置 `Armed = true`（表示「处于进游戏载入期」），`Hide()` 清 `Armed`。`GameScene.Process()` 每帧检查：

- 世界没就绪且 `Armed` → 重跑 30 秒超时保护（服务端不回应/地图永远下不来时不至于永远卡着）；世界就绪 → `Hide()`。

因此点开始之后，无论卡在哪个阶段（网络慢、地图大、微端在下资源），玩家一直看到的是载入画面，而不是黑屏。

挂载点：`SelectScene.StartGame()`（点开始立刻显示；游戏资源没加载完时 `Process()` 轮询 `Libraries.Loaded` 并刷新进度文字，就绪后 `TrySendStartGame()` 自动发出进入请求；`StartGame` 回包 result=4 时在新建的 `GameScene` 上重新挂一次再 `Dispose()` 选人场景）、失败/延迟/封号分支各自 `Hide()` 并复位 `_startPending`；`GameScene.Dispose()` 里也收一次，避免 `Armed` 状态带到下个场景。「15 秒无回包自动撤掉」的保护只从**进入请求真正发出**那一刻起算——资源加载再久也不会被它误杀。

**层级（永远在最上面）**：载入画面**不挂到任何场景的控件树上**（`MirImageControl` 不设 `Parent`），而是由 `CMain.RenderEnvironment()` 在 `ActiveScene.Draw()` 之后调用 `LoadingScreen.DrawOverlay()` 单独画一遍。原因是游戏 UI（主面板、技能条、物品栏、聊天框）都是场景的子控件，会被烘焙进**场景纹理**里按控件顺序绘制——载入画面一旦也当子控件，就会被挤在技能条后面（技能条盖在载入背景上）。改成场景画完再单独画一遍之后，无论场景怎么切、子控件怎么排序，载入画面都在最上层；同时也就不需要「换场景后重新挂回」那套逻辑了（控件根本不在场景里，切场景不会丢）。

### 2.12 游戏中画面规律性「发暗闪烁」的修复（读 lib 素材时）

**现象**：进游戏后画面每隔约 0.1 秒整屏变暗一帧（反复闪，尤其微端正在按需读取怪物/装备 lib 的时候）。录屏逐帧分析证实：暗帧不是变黑，而是**整帧被压到 ~50% alpha**——白色聊天框变半透明、能透出后面的地图。

**根因**（一处典型的「渲染状态泄漏」）：

1. 隐身单位按半透明绘制：`DXManager.SetOpacity(0.5F)` 会把 D3D 切到 **BlendFactor 恒定 alpha 混合**模式——从这个调用起，**这一帧里后面画的所有东西**（其他对象、UI 面板、最终整屏合成）全部按 50% alpha 混合，直到代码调用 `SetOpacity(旧值)` 恢复。
2. `MonsterObject.Draw()` 里恢复调用之前有一行提前返回：`if (BodyLibrary == null || Frame == null) return;`——怪物 lib 未加载/微端正在读取时恰好命中，**恢复被跳过，状态泄漏出去**。
3. 底板纹理每 100ms 重建一次，每次重建走到这帧的用户半透明绘制时再把状态推到 0.5 → **暗帧以 0.1 秒周期反复出现**，与录屏测到的暗帧间隔完全一致。

**修复**（两道保险）：

| 位置 | 改动 |
|---|---|
| `MirObjects/MonsterObject.cs` `Draw()` | 判空 `BodyLibrary == null \|\| Frame == null` **移到 `SetOpacity` 之前**——素材没就绪直接跳过，不再污染渲染状态 |
| `MirGraphics/DXManager.cs` + `Forms/CMain.cs` | 新增 `DXManager.ResetDrawState()`，每帧 `RenderEnvironment()` 开头强制复位混合模式与透明度——今后任何状态泄漏最多影响当帧局部，不会再持续发暗 |

**验死标准**：进新图、微端补资源期间画面应始终稳定；隐身单位仍正常半透明显示。

### 2.13 全屏退出后进程驻留（已修复）

**现象**：窗口模式退出一切正常；切到（独占）全屏后退出，游戏界面消失了，但任务管理器里 `Client.exe` 还在，只能手动结束。

**定位过程**（临时写了一个 `Client/ExitTrace.cs` 做全链路埋点，跑一次即定位；**问题解决后该工具与所有埋点已全部删除**）：

日志显示关闭流程**每一关都走完了、没有任何异常**：

```
CMain_FormClosing 进入 → 判定：可以退出 → Settings.Save → DXManager.Dispose(0.4s) → SoundManager.Dispose
→ CMain_FormClosing 返回 → 启动器 AMain_FormClosed → MoveOldFilesToCurrent → 即将 Environment.Exit(0)
```

也就是说：**卡的不是关闭逻辑，而是「进程终止」本身**。

第一轮猜想「`FormClosing` 里的空引用异常弹了个全屏下看不见的对话框」被日志否掉了——日志里一条 `UI线程未处理异常` 都没有。

**真正的根因**：`Environment.Exit(0)` 最终会调用 Win32 的 `ExitProcess`，而 `ExitProcess` 必须**逐个卸载进程里已加载的 DLL**（每个 DLL 的 `DllMain(DLL_PROCESS_DETACH)` 都会被调用一次）。只要其中任何一个不返回，进程就永远停在 `ExitProcess` 里——界面已经没了、进程还在。全屏独占模式下 D3D9 设备/显示驱动的卸载路径和窗口模式不同，正是最容易卡在 `DllMain` 的对象；启动器常驻的 WebView2 运行时也是同类嫌疑。

这解释了「窗口模式正常、全屏驻留」：两者**差在 DLL 卸载路径，不在退出逻辑**。

**修复**（`Client/Program.cs` 新增 `HardExit()`，替换全部 `Environment.Exit(0)`）：

| 位置 | 改动 |
|---|---|
| `Program.HardExit()` | ① 后台线程限时 1.2 秒释放启动器 WebView2（只为不残留 `msedgewebview2.exe`）；② **`Process.GetCurrentProcess().Kill()`** —— 走 `TerminateProcess` 由内核直接回收进程，**不卸载任何 DLL、不等待任何线程，不存在被卡住的可能** |
| `Forms/AMain.cs` `AMain_FormClosed()` | 各清理步骤单独 try/catch，末尾调用 `Program.HardExit()`（原来调 `Environment.Exit(0)`）；新增 `ReleaseBrowser()` 释放 WebView2 |
| `Program.cs` `Main()` | `Application.Run` 返回、`Settings.Save()` 之后（非自重启时）也调 `HardExit()` —— 不开启动器直接跑客户端时同样收口 |

**为什么不用「3 秒兜底强杀」那套**：兜底线程注册在关闭流程里，而 `ExitProcess` 一旦进入 DLL 卸载阶段会先把其它线程全部结束，兜底根本没机会执行。必须在源头就不用 `ExitProcess`。

**验证标准**：全屏下「登录 → 小退 → 立刻退出」应秒退；任务管理器里不留 `Client.exe`，也不留 `msedgewebview2.exe`。

> 注意：`TerminateProcess` 属于内核级直接回收，不做托管层收尾（不发 `ProcessExit`、不跑 finalizer）。因此**退出前的落盘必须在 `HardExit()` 之前完成**——`Settings.Save()` 已在 `CMain_FormClosing` / `Program.Main` 中先行调用，顺序不要调换。

### 2.14 改了 `Mir2Config.ini` 的 `IPAddress`，客户端却不读

**现象**：把客户端 `Mir2Config.ini` 里的 `IPAddress` 改成服务器地址，客户端还是往本机 `127.0.0.1` 连。

**原因**：客户端读这个 IP 时前面有一道开关（`Client/Settings.cs`）：

```csharp
//Network
UseConfig = Reader.ReadBoolean("Network", "UseConfig", UseConfig);
if (UseConfig)                                   // ← 开关为 False 时，下面两行根本不执行
{
    IPAddress = Reader.ReadString("Network", "IPAddress", IPAddress);
    Port      = Reader.ReadInt32("Network", "Port", Port);
}
```

`UseConfig` 的**默认值就是 `False`**，所以只要 ini 里没写成 `True`（或那行被删了），`IPAddress` / `Port` 就被忽略，用编译进去的默认值 `127.0.0.1:7000`。

```ini
[Network]
UseConfig=True          ; ← 必须显式写成 True，IPAddress 才会生效
IPAddress=192.168.2.253
Port=7000
```

两个补充事实：

- **客户端从头到尾不会写 `[Network]` 段**（`Settings.Save()` 只写 Graphics / Sound / Game / AutoPlay / Chat / Filter / MicroClient / Launcher），所以这个开关不会被游戏改掉，只能手工设。
- **`Mir2Config.ini` 里的三个地址互相独立**，改哪个只影响哪个，不会联动：

| 配置项 | 作用 | 默认值 |
|---|---|---|
| `[Network] IPAddress` + `Port` | 游戏服务器（登录服，TCP 7000） | `127.0.0.1:7000` |
| `[Launcher] Host` | 启动器的补丁/更新站（HTTP） | `http://127.0.0.1/mir2/cmir/patch/` |
| `[MicroClient] Host` | 微端资源服务（HTTP 5679） | `http://127.0.0.1:5679/` |

> **改 ini 前先关掉客户端和启动器。** `IniReader` 是「启动时读进内存、之后整文件重写」的实现（`Shared/Functions/IniReader.cs`），客户端/启动器**退出时会把内存里的那份快照写回文件** —— 运行期间手改的 ini 会被覆盖掉，看起来就像「改了没用」。

| ------------------------------------------------------------ | --------------------------------------------------------------------------------------------- |
| 客户端设了高分辨率，进游戏又变回 1024                                        | 服务端 `MaxResolution` 太小，或改完没重启服务端                                                              |

| 点「开始」要等很久才出登录界面                                              | 已修（见 §2.11）：着色器/清单/补丁列表都不再阻塞启动路径。若仍慢，看 `MicroClient.log` 里资源清单多久到手                            |
| 玩家端一直卡在某处下载                                                  | 单个资源超时是 `Timeout` 的 4 倍（默认 32 秒），后台线程在跑、不会卡画面。进新地图等待上限是 30 秒                                  |
| 全屏下点「退出游戏」进程关不掉                                          | 已修（见 §2.13）：`Environment.Exit` 会卡在 `ExitProcess` 的 DLL 卸载阶段，改用 `TerminateProcess` 硬回收。若还遇到，按 §2.13 的埋点方式临时加日志再定位                       |
| 进游戏后发现某个怪物/装备晚半秒才显示                                          | **正常现象**。这就是按需加载 —— 后台刚把它下完。第二次遇到就不会了                                                         |
| 想让资源补得更快                                                     | 调大 `Concurrency`（1~8），或 `RateLimit=0` 取消限速                                                    |
| 想让资源补得「更不打扰」                                                 | `RateLimit=512`（每个线程 512 KB/s），玩家几乎感觉不到带宽被占                                                   |
| 想确认「微端到底有没有在下」                                               | 把 `Hint` 改成 `True`，聊天框会显示「微端已启用 / 资源补齐完成」；或直接看 `MicroClient.log`                              |
| 资源服务启动失败                                                     | 5679 端口被占用。用 `http://+:5679/` 没做 urlacl 授权**不再失败**，会自动降级到纯 Socket（详见 §2.8）                    |
| **改成固定 IP 后，本机反而进不去游戏**                                      | `IPAddress` 绑的是那**一个**网卡地址，回环 `127.0.0.1` 不再监听。改成 `0.0.0.0` 即可（详见 §2.8）                       |
| **`HTTPIPAddress` 换成具体 IP 后，报「拒绝访问 (5)」**                    | http.sys 的 URL 保留项没登记。只有 `127.0.0.1`/`localhost` 免登记。新版会自动改用纯 Socket，不再中断（详见 §2.8）            |
| **`HTTPIPAddress` 写成 `http://0.0.0.0:5679/`，报「不支持该请求 (50)」** | http.sys 不认 `0.0.0.0` 这个主机名，要写 `+` 或 `*`。新版会自动翻译成 `+`（详见 §2.8 坑三）                             |
| **`IPAddress` 填了个不存在的 IP，服务端起不来**                            | 报 `10049 在其上下文中，该请求的地址无效`。填的地址必须在 `ipconfig` 里真实存在                                            |
| 服务端在跑，但玩家资源全下载失败                                             | 看启动日志里「微端资源服务 已开启: ...」那行拿到真实监听地址；再确认防火墙放行了 5679、玩家端 `Host` 指向服务端地址（不是 `127.0.0.1`）           |
| **关了「启用HTTP服务」，HTTP 监听却还在跑**                                 | 正常现象：微端资源服务（`EnableResourceService`）本身就需要监听来下发资源。见 §2.3 的两个开关对照表                              |
| 「微端资源服务 已开启」，但局域网玩家连不上                                       | 多半是**防火墙没放行 5679**（绑 `0.0.0.0` 不需要管理员权限，但入站仍要放行）。跑一次一键配置脚本的 [2] 即可                            |
| 启动日志说「http.sys 通道不可用，已自动改用纯 Socket 模式」                       | 正常，不是故障。想要内核态 http.sys 就登记 urlacl 或以管理员运行（详见 §2.8）                                            |
| 改了 `Setup.ini` 但重启后毫无变化                                      | **服务端运行期间别手改 ini** —— 它退出（或关闭「设置」窗口）时会把内存里的旧值写回。先关服务端再改，或直接用「设置」窗口（见 §2.8）                    |
| 同一个网络里第 6 个玩家掉线                                              | `MaxIP=5` 是**每个 IP 的最高连接数**。同一路由器/网吧出口后面的玩家共用一个公网 IP，超了会被临时封 5 秒（`IPBlockSeconds`）。局域网人多时把它调大 |
| 上百人同时上线时资源补得很慢                                               | 先看 §2.9。服务端处理能力已不是瓶颈，多半是服务器**上行带宽**不够                                                         |
| 资源服务把磁盘/CPU 占用拉高                                             | 调小 `ResourceMaxConcurrent`（如 32），或把资源目录放到独立 SSD 上                                             |
| 外网玩家卡在某个资源上，日志写着"下载失败"                                       | 看 §2.10。多半是那个文件特别大（最大的 588MB），旧版固定 32 秒超时会必然失败                                                |
| 微端包体积莫名其妙变大了                                                 | 玩家跑过之后，按需下载的资源会落进包目录。用 `Tools/restore_micro_package.py` 还原                                    |
| 改了图库但客户端还是旧的                                                 | 客户端本地已有该文件时不会重新下载（按需下载只补缺失）。删掉本地旧文件即可                                                         |
| **改了客户端 `Mir2Config.ini` 的 `IPAddress`，客户端还是连本机** | `[Network]` 段里的 `UseConfig` 不是 `True` 时，这个 IP **根本不读**，用默认 `127.0.0.1`。改成 `UseConfig=True`（见 §2.14） |
| 改了 `IPAddress`，但启动器/微端还是连老地址 | 三个地址互相独立：`[Network] IPAddress`（游戏服 7000）、`[Launcher] Host`（更新站）、`[MicroClient] Host`（资源站 5679）。见 §2.14 |
| 运行期间手改 ini，重启后发现又被改回去了 | 客户端/启动器的 `IniReader` 退出时会**整文件写回**内存快照。改之前先关客户端和启动器（见 §2.14） |

## 六、需要注意

1. **服务端要重启**：`Setup.ini` 的改动重启才生效。
2. **微端客户端首次进新场景会卡一下**：那是在下载资源（地图通常几 MB）。之后就有本地缓存，不再卡。
3. **你自己的客户端 `Enabled=False`**：本机资源完整，开微端没有任何收益，只多一次启动时的清单请求。
4. **`ResourcePath` 是微端的「仓库」**：它必须指向一份**完整**资源。如果哪天你更新了客户端资源，服务端的仓库也要同步，否则玩家下载到的是旧资源。
5. **对外开服别填具体 IP**：`IPAddress=0.0.0.0` + `HTTPIPAddress=http://+:5679/`，并且 `HTTPIPAddress` 必须先登记 URL 保留项，否则 HTTP 服务静默起不来（见 §2.8）。
