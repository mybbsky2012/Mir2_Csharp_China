微端服务剥离可行性 & 负载能力评估

Korean Mir2 (Crystal / .NET 8) · 实测环境：8 核 / 23.8 GB 内存 · 2026-10-10

结论速览

① 微端服务可以剥离，而且成本很低——资源下发的三个接口与游戏世界零耦合，项目里已有的 HttpBenchHost 就是"同一份代码独立进程跑"的现成证明。

② 微端服务本身不会拉爆服务器——实测 100 个玩家同时下载 2000 次请求：0 失败，进程仅占 1.7 核、~130 MB 内存。

③ 真正的瓶颈是服务器上行带宽，不是服务端处理能力。而"会不会被拉爆"取决于同时下载的人数与上行带宽之比，与"在线人数"无直接关系。

一、现状：微端服务跑在哪

微端（按需下发客户端资源）目前内嵌在游戏服务端 Server.exe 进程里，随 Envir.Start() 一起启动：

Envir.cs:582   if (Settings.StartHTTPService || Settings.EnableResourceService)
Envir.cs:584       http = new HttpServer();
Envir.cs:585       http.Start();              // 另起线程监听

线上配置（Configs/Setup.ini）：

配置项当前值含义

二、剥离可行性：为什么可行

代码依赖极干净

微端服务的实现只有三个文件，它们的对外依赖是这样的：

文件行数依赖能否独立
HttpAbstractions.cs~250无可独立
HttpService.cs821Settings 的 7 个配置项 + 日志可独立
SocketHttpServer.cs486日志可独立
HttpServer.cs347上述三者 + Envir.Main仅管理接口耦合

关键在于：HttpServer 里的耦合只出现在 账号注册 / 广播 / 改名 三个管理接口（调用 Envir.Main）。而微端真正要用的三条路由——

  • /resource?f=... —— 下发单个资源文件（流式）
  • /resindex —— 资源清单（客户端据此推算该有哪些文件）
  • /resinfo —— 状态探测

全程不碰游戏世界，只读磁盘上的静态文件 + 读几个配置项。所以"剥出来"在架构上是干净的切割，不是硬拆。

现成的活证明：Tools/HttpBenchHost 通过反射加载 Server.Library.dll 里真实的 HttpServer，在独立进程、独立端口上把微端服务跑了起来——本次压测就是用它做的。它已经证明"同一份代码能在 Server.exe 之外运行"。

三、三种剥离方案

方案 A · 独立宿主进程 推荐

把 HttpBenchHost 正式化为「微端资源服务」，独立进程运行。

  • 游戏服务端改 EnableResourceService=False
  • 客户端 Host 指向新进程/新机器
  • 可单独部署到另一台机器

优点：零重复代码（与线上同一份实现，改一处两边生效）、进程隔离、改动最小。
缺点：需带 Server.Library.dll（1.2 MB）。

方案 B · 彻底解耦工程

新建独立项目，抽出三个 HTTP 文件 + 精简配置类，不引用 Server.Library.dll。

  • 把 Settings.X 换成精简的 MicroSettings
  • MessageQueue 换成简单的控制台日志

优点：最纯净的依赖树，可编译成单文件小工具。
缺点：需要改代码，且此后有两份 HTTP 实现需要同步。

方案 C · 交给 CDN / 对象存储（生产级最优）
微端资源是纯静态文件，天然适合 CDN。把 12 GB 资源上传到对象存储（COS/OSS）并开 CDN，客户端 Host 直接指向 CDN 域名 —— 服务器上行带宽消耗降为 0，扩容无上限，且比自建更抗并发。若预算允许，这是最彻底的"剥离"。

五、会不会被拉爆？分层看

① 游戏逻辑线程：不受影响

这是本次排查最关键的发现——游戏服务端（Server/ 下除 Utils/ 外的全部代码）完全没有使用 Task.Run、async/await、ThreadPool：

GameServer 线程模型
├── WorkLoop          → new Thread(WorkLoop)   专用线程：网络收发 / 主逻辑 / 存档
├── MobThreading[i]   → new Thread(ThreadLoop) 专用线程：怪物 AI（Multithreaded=True 时）
└── http              → new Thread(Listen)     专用线程：微端监听
                        └─ Task.Run(...)       ▸ 线程池：微端请求处理（唯一用线程池的地方）

★ 游戏逻辑与微端服务分属两套完全独立的线程体系，不存在线程池饥饿。

所以微端不会通过线程池把游戏主循环饿死——它们根本不共享。

② CPU / 磁盘：同机会互相挤占

若微端与游戏服务端跑在同一台机器上，两者争抢同一份 CPU 和磁盘：

  • 微端峰值吃 2.4 核（8 核机器的 30%）→ 主循环 tick 与网络处理会被挤慢 → 玩家端表现为轻微卡顿
  • 微端读盘峰值 387 MB/s → 若 E 盘是机械硬盘，这个量级足以把 IO 打满，连带游戏存档、地图加载变慢

→ 这正是"剥离到另一台机器"的核心价值：进程隔离在单机上不能隔离 CPU 和磁盘，只有物理隔离才能。

③ 上行带宽：真正的瓶颈

本次压测跑在环回接口上（1077 MB/s），这个数字没有任何现实参考价值。真实世界里，微端的极限由服务器上行带宽 ÷ 同时下载人数决定：

表中为"每人平分带宽"的理想值。参考：一个 100 MB 的图库，在 0.125 MB/s 下需要 13 分钟才能下完。

两个加剧因素：
1. 客户端 RateLimit=0（不限速）→ 单个玩家可独自吃满整条上行链路；
2. 下载是脉冲式的——平时几乎为零，一次版本更新会让所有在线玩家同时补资源，正是最容易打满的时刻。

六、建议

  1. 先测上行带宽——这是唯一决定"会不会被拉爆"的数字。若 ≥100 Mbps 且同时在下载的人不超过十几个，现状完全够用，不必剥离。
  2. 给客户端设限速：把 Mir2Config.ini 的 RateLimit 从 0 改为 100~200（KB/s）。虽然玩家可自行修改，但能挡住绝大多数人，且明显削平更新日的带宽尖峰。
  3. 要剥离就选方案 A（独立宿主进程），改动最小、代码同源。前提是换一台机器部署才有意义——同机双进程隔离不了 CPU 和磁盘。
  4. 上线量级大就直接上 CDN（方案 C）：静态资源交给对象存储 + CDN，服务器带宽消耗归零，且是最省心的长期方案。
  5. 保留服务端闸门：ResourceMaxConcurrent=64 是防"磁盘被打爆"的最后一道闸，不要为了追求速度把它调得过高。
