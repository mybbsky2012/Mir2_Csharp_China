### 组队机制的关键事实（复用原生，不重写）
- `MapObject.GroupMembers`（`public List<PlayerObject>`）就是队伍本身，**[0] 是队长**，无独立 Group 类；`PlayerObject.AddMember/GroupInvite(bool)/LeaveGroup/DelMember`。

## 跟队假人「追上 + 帮 PK」（16:25-16:35）
用户需求：① 玩家离组队假人很远了，假人要跟上；② 玩家 PK 其他假人/玩家时，跟队假人要跟着帮打；③ 跟队假人要能帮玩家 PK 其他假人和玩家。

### 关键发现：服务端没有「玩家正在打谁」的字段
- `HumanObject.Target` 只在宠物/英雄跟随主人目标（`PMode == FocusMasterTarget`）时被赋值，**玩家自己攻击不会写 Target**。
- `MapObject.LastHitter` / `LastHitTime`（10 秒窗口）是**受害者侧**字段，谁最后打了他就记谁 —— 会被**假人自己的一击顶掉**（我们打一下，队长的记录就没了），不能单独用来判断「队长在打谁」。
- 结论：必须在**攻击者侧**新增字段。已加在 `HumanObject`：
  ```csharp
  public MapObject RecentPvPTarget;   // 我最近主动打了哪个玩家
  public long RecentPvPTime;          // 15 秒有效期
  ```
  写入点 3 处（都加了 `Race == ObjectType.Player` 过滤，怪物不记，避免无谓开销）：
  1. `HumanObject.Attack()` 肉搏命中循环（`cell.Objects` 里那段 `IsAttackTarget && !IsFriendlyTarget`）；
  2. `HumanObject.Magic()` 解析出 `target` 之后那段同样条件的分支（雷电/火符等单体）；
  3. `HumanObject.RangeAttack()`（同款分支，弓箭/远程武器）。
  过期清理放在 `HumanObject.Process()` 开头（`Envir.Time > RecentPvPTime || Node == null` → 置空），否则会一直攥着一个已下线的对象。

### 脑内的协助判定
- `HasLeaderConflict(h)`：`leader.RecentPvPTarget == h`（队长在打他）或 `leader.LastHitter == h`（他在打队长）或**遍历 `GroupMembers` 看谁最近被 h 打过**（队友不能被白打）。
- `IsAssisting(h)` = `HasLeaderConflict(h)` **或** `h == _assistTarget && Envir.Time < _assistUntil`（12 秒「咬住不放」宽限）。
- **自己给自己续期的坑**：宽限窗口必须只由 `HasLeaderConflict` 续期。要是在 `CombatUpdate` 里写成 `if (IsAssisting(h)) _assistUntil = now + hold;`，`IsAssisting` 又包含「宽限未过期」分支 → 无限续期，架永远打不完。已改成 `if (HasLeaderConflict(human)) { _assistTarget = human; _assistUntil = now + AssistHoldTime; }`，宽限只在**信号刚断**时兜 12 秒。
- `FindAssistTarget(leader, range=12)`：以**队长位置**为中心螺旋扫描 `Race == ObjectType.Player` 的对象，过滤 死亡/隐藏/自己/队长/`GroupMembers.Contains`/`!IsAttackTarget(p)`/离自己 > range+4；和平地图（`Info.NoFight`）和自己处于安全区时直接 return null。
- `_duelUntil` 的 45 秒收手限制：协助中（`human == _assistTarget && now < _assistUntil`）自动续 45 秒；「6 秒没掉血就换目标」这条对协助对象放宽到 10 秒轮询（对方可能只是皮厚）。

## 客户端跑动卡顿排查 + 假人降频优化（21:09-21:20）
用户问：客户端跑动经常卡顿什么原因？会不会是组队假人多 + 同时加载微端资源。

### 服务端侧的三个关键事实（读代码得出）
1. **主循环是 busy loop，无 sleep**（`Envir.WorkLoop`）：`while (Running)` 里每轮最多花 20ms 扫 `Envir.Objects`，`LastRunTime = Time - startTime` 就是「一整轮的对象处理耗时」，GUI 右下角显示的**「延迟周期」**就是它（`SMain.cs` → `CycleDelayLabel`）。这个值一大，玩家发来的走/跑/攻击包要排队等下一轮 → 客户端表现为**跑一步顿一下、偶尔回拉**。
2. `HumanObject.SetOperateTime() => OperateTime = Envir.Time` —— 真人和假人**每个主循环轮次都会被 Process 一次**（原版设计）。所以「50 个假人」原本 ≈ 「50 个真人」的主循环开销。
3. `Map.Players` 里包含 `FakePlayerObject`；`MapObject.Broadcast()` / `Map.Broadcast(p,loc)` / `Map.BroadcastNPC()` 会**白扫所有假人**（它们的包被 BotConnection 直接丢掉）。地图上每条广播多扫 N 次 InRange。

### 本次做的三件事
- **假人降频**：新增 `FakePlayerObject.SetOperateTime()` → `OperateTime = Envir.Time + Random(130, 280)`。把假人主循环开销压到约 1/5，且随机错开落点避免同帧尖峰。安全性论证：`ProcessRegen`（有 `CanRegen`/`RegenTime` 闸）、`ProcessPoison`（`poison.TickTime` 闸）、`ProcessBuffs`（buff 自带时间）、`MapObject.Process` 的 `ActionList`（`action.Time` 闸）**全部自带时间闸**，调用频率变低只会让效果晚 200ms 触发，不会漏掉或重复。大脑本来就 380~700ms 一次，实际决策频率不变。
- **广播跳过假人**：`MapObject.Broadcast` / `Map.Broadcast(p,Point)` / `Map.BroadcastNPC` 里 `if (player is FakePlayerObject) continue;`。
- **性能探针** `FakePlayerPerf`（放在 `FakePlayerManager.cs` 文件末尾，同一个 namespace）：
  - `NoteBotProcess/NoteBrain/NoteBroadcastSkipped` 三个 long 累加（Stopwatch.GetTimestamp 计时，只在 FakePlayerObject.Process 里用）；
  - `Sample(cycleDelay)` 每秒一次（挂在 `FakePlayerManager.Process` 的 1 秒节流处，在 `!Enabled` 早退**之后**），换算成「每秒次数/微秒」快照并记录 `CircDelayPeak`；
  - GM 命令 `@假人 性能` / `@假人 性能 重置`（`FakePlayerManager.PerfReport()` / `ResetPerfPeak()`，`PlayerObject` 的 `case "假人"` 里加 `case "性能"/"perf"`）。
  - 报告输出：主循环周期当前/峰值、世界对象数、在线玩家/假人数、假人 Process 每秒次数与 ms（换算成 % CPU）、大脑 Tick、跳过的广播次数。判读：假人个位数 ms → 与假人无关；周期上三位数 → 服务端自己在卡。

### 结论（给用户的判断顺序）
微端边跑边下资源（只在第一次经过的地方卡，重走一遍就顺）> 同屏对象多掉帧 > 网络抖动 > 服务端主循环拥塞 > 客户端本机问题（机械盘/杀软/DirectDraw/输入法）。
服务端微端资源服务本身不用担心的依据：`HttpService` 有 `TransferGate` 并发闸（`ResourceMaxConcurrent`，最小 4）、流式发送不全块读内存、监听在独立线程 + 提高 ThreadPool 最小线程数；`ResourceVerboseLog` 默认关（排障再开）。
A/B 最干脆：`Enabled=False` 重启跑同一条路线 vs `Enabled=True` 再跑一次。

## 报告聊天框溢出修复 + 登录点随机挑选（22:00-22:05）

`Client/MirScenes/Dialogs/MainDialogs.cs` 的 `ChatDialog.ReceiveChat()`（784 行起）**完全不处理 `\n`** ——

服务端把多行报告（内嵌 \n）当一条消息发过去，客户端把它揉成一整段长文本按宽度乱折 →
串行、重复感、超出聊天框。这就是截图问题的根因。
