## 一、改造概述

### 1.1 背景与目标

羽化登仙是本服的高阶成长线：玩家完成羽化后，人物外观整体切换为独立的"仙体"素材（另一套人物、发型、武器、坐骑、鱼竿与内观立绘），并获得按重数递增的属性加成。改造前的状态是"素材已导入、但系统只接通了一半"，存在四类问题：

1. **外观不完整**：只有部分职业/档位能正确显示；骑乘、持竿、内观会掉回原版素材或画成固定仙兵。
2. **规则缺失**：未羽化角色可以直接穿上羽化专属装备，客户端仅凭装备 Shape 就接管仙体外观，等于免 BUFF 白嫖。
3. **判定错误**：羽化武器使用了 2000 段新 Shape，而多处职业判定仍按旧的 `Shape / 100` 规则，导致刺客/弓箭手"必须佩带适合的武器"、羽化弓射不出箭。
4. **数据隐患**：羽化状态寄存在自定义 BUFF 槽位，未知 BUFF 类型会让整个账号库回退 `.bak` 并导致服务器无法启动。

本轮改造的目标，是把羽化登仙做成一条**闭环**：装备能穿、外观正确、属性可配、退回可控、异常不炸服。

### 1.2 系统组成

| 子系统 | 职责 | 主要实现位置 |
|---|---|---|
| 装备体系 | 羽化专属盔甲/武器，Shape 编码区分职业与档位 | 物品库 + `PlayerObject.IsHumUpEquipShape` |
| 外观体系 | 按 Shape 切换人物/发型/武器/坐骑/鱼竿图库 | `Client/MirObjects/PlayerObject.cs`、`MLibrary.cs`、`Frames.cs` |
| 属性体系 | 一重~十重的属性加成 | `BuffSystem.ini` + `BuffType.羽化一重~十重` |
| 规则体系 | 未羽化禁穿、退回前必须脱装 | `HumanObject.CanEquipItem`、`SetHumUpStage` |
| 命令体系 | NPC 脚本与 GM 命令 | `NPCSegment.cs`、`PlayerObject.cs` |
| 存档体系 | 旧 BUFF 编码迁移与容错 | `CharacterInfo.MigrateHumUpBuffs`、`BuffInfo.Unknown` |

### 1.3 玩家侧完整链路

1. 玩家通过 NPC 完成羽化（`HUMP` / `@HUMUP`），身上获得"羽化登仙"标记 + "羽化登仙·N 重"属性 BUFF。
2. 客户端检测到羽化 BUFF，`SetHumUpLibraries()` 接管图库：人物走 `UpCArmour`/职业羽化库，发型走 `UpCHairs`，武器走 `UpCWeapon`，坐骑走 `UpMount`，鱼竿走 `UpFishing`。
3. 玩家穿上羽化专属装备（Shape 1001~1059 / 2001~2059），客户端据此选择具体档位素材；服务端在穿戴入口校验"必须已羽化"。
4. 战斗中属性由 BUFF 提供；退回羽化前必须先脱下全部羽化装备，避免"BUFF 没了但外观还在"。

## 二、技术架构

### 2.1 客户端渲染链路

羽化外观不改变任何物品 Shape 定义，全部由 `PlayerObject.SetLibraries()` 在每帧前重新解析：

```
SetLibraries()
  └─ SetHumUpLibraries()                    // 判定是否处于羽化外观
       ├─ 读 HumUpStage（自己走 BuffsDialog，别人走 ObjectPlayer.Buffs）
       ├─ 盔甲：IsHumUpEquipShape(armourShape) ?
       │        ├─ 是 → Up{职业}Armour\0N.Lib（N = 档位）
       │        └─ 否 → 按 HumUpRideTier 映射选 UpCArmour（通用库）
       ├─ 发型：UpCHairs（骑乘/通用时按档位映射，女半 +1112）
       ├─ 武器：2000 段 → Up{职业}Weapon\0N.Lib；鱼竿 → UpFishing\00M|00F
       ├─ 坐骑：UpMount\NN.Lib
       └─ Frames：HumUpCommon（通用帧表）/ HumUpPlayer（职业帧表）
```

绘制阶段由 `_humUpMount`、`_humUpFishing`、`HumUpLook` 三个标记决定走哪条分支，避免每帧重复读 BUFF 状态造成"身体已换库、武器还按旧方位垫层"的自相矛盾。

### 2.2 服务端数据与校验链路

服务端**不参与外观判定**（只把 `Looks_Armour = Shape` 原样下发），但承担三件事：

1. **准入校验**：`CanEquipItem` 拦截未羽化角色穿戴羽化装备（英雄、假人走同一入口）。
2. **状态管理**：`SetHumUpStage` 统一负责加/减/清零重数，并在退回前检查是否还穿着羽化装备。
3. **存档迁移**：`CharacterInfo` 读档时把旧 BUFF 编码就地映射为新编码，保证在线前选人界面立绘也正确。

### 2.3 共享层

`BuffType` 枚举是客户端与服务端共用的协议常量：羽化状态要随 `ObjectPlayer.Buffs` 广播给周围玩家，因此**重数必须编码在枚举值本身**，不能放在 `Buff.Values`（`Values` 不随视野同步）。

## 三、编码规范（核心约定）

### 3.1 装备 Shape 编码

```
盔甲：1000 + 职业索引 × 10 + 档位     → 1001 ~ 1059
武器：2000 + 职业索引 × 10 + 档位     → 2001 ~ 2059
职业索引：0 通用 / 1 战士 / 2 法师 / 3 道士 / 4 刺客 / 5 弓箭
档位：1 ~ 8（对应素材 \01~08.Lib；00 是素体，不作为档位）
```

判定口径在客户端与服务端**完全一致**（`clsIdx ≤ 5 && tier ≥ 1 && tier ≤ 8`），任何一边改动必须同步，否则会出现"服务端能穿、客户端不认"的错位。

## 四、功能改动明细

### 4.1 外观：盔甲档位从 3 档放宽到 8 档

- **文件**：`Client/MirObjects/PlayerObject.cs` → `IsHumUpEquipShape`
- **改动**：`tier ≤ 3` → `tier ≤ 8`，注释同步为各职业实际 Shape 段。
- **原因**：素材 `Up*Armour\00~08.Lib` 本就齐全，代码只放行前 3 档，导致 4 档以上被判定为"非羽化装备"，羽化状态下身体强制回落到 01 档，表现为"设 1034 显示的还是 1031"。

### 4.2 外观：武器按档位选库

- **文件**：`PlayerObject.SetHumUpLibraries`
- **改动**：羽化武器不再恒用 `01.Lib`，改为按 `GetHumUpEquipClass` 取出的档位拼 `Up{职业}Weapon\0N.Lib`。
- **配套**：11-11 写库时为 29 件武器分配了连续档位（战 5 / 法 4 / 道 4 / 刺 8 / 弓 8）。

### 4.3 外观：骑乘接入 UpMount 与骑乘姿势

- **文件**：`MLibrary.cs`、`PlayerObject.cs`、`Frames.cs`
- **加载**：`MLibrary` 新增 `UpMounts`（`InitLibrary` 扫描，微端清单自动生效）与 `UpFishingMan/Woman`（男女分文件，手动 new，索引 = Shape - 49）。
- **姿势**：骑乘时身体切 `UpCArmour` 骑乘区（792 起：站 4 / 走 8 / 跑 6 / 被击 3 / 攻 6 帧），马腿帧与身体 `FrameIndex` 逐帧同步，取代早期按时间独立步进（会出现"人不动马在跑"）。
- **配色**：职业羽化甲没有骑乘帧，必须用通用库；为不让各职业/档位穿出"别人的衣服"，用 72 维色彩直方图（24 色相 × 3 明度带）把 5 职业 × 10 档映射到最接近的通用档，落成 `HumUpRideTierMap` 5×10 静态表。
- **特效**：`SetEffects()` 原实现 `if (RidingMount) return;` 会把羽化特效整段跳过。改为拆开处理——头上飞龙（Effect 1020）骑乘保留、脚下光环（Effect 990）骑乘不画。

### 4.4 外观：鱼竿（本轮改动最密集）

| 改动 | 旧 | 新 |
|---|---|---|
| 钓鱼身体段 | 632 / 696 / 744（照搬原版 CArmour） | **600 / 664 / 728**（羽化库整体前移 32 帧） |
| 竿段：收线 | 112（实际是等待段 dir6/7） | **128** |
| 攻击/施法竿段 | 256 静持（死竿） | **320 挥砍**（8 方向全有效，自带速度线） |
| 攻击/施法身体段 | 896 双手举高施法 | **448 单手挥砍** |
| 竿绘制位置 | 素材锚点 + 像素补偿（+8/-8、+4/-4） | **素材原锚点，零补偿** |
| 跑动/行走竿 | 跟随静持段（几乎逐像素相同 → 死竿） | **弧形摆臂位移表**（8 方向 × 6 帧） |
| 持竿身体库 | 仅"穿羽化甲/裸体"才切通用库 | **持竿一律切通用库**（含穿普通甲） |

**钓鱼段位是怎么确定的**：先用"竿像素到身体像素的 BFS 最小距离"全库扫描——正确配对的每一帧距离都应为 0。扫描结果显示 `UpCArmour` 的真实钓鱼段是 600/664/728（与竿 0/64/128 恒定相差 600），而 632 段与任何竿段都配不上（最小 5.9px，最大 25px），这正是"鱼竿乱飞"的根源。

**为什么删掉像素补偿**：竿帧的 `fx/fy` 与身体帧共用锚点体系，锚点即握点。早期"抬高 5~10px"的反馈是在身体错误使用 896（双手举高）段时观察到的；身体改成 448 后，原补偿反而把竿推离手，表现为"竿跟在身边"。实测竿 320 × 身体 448 每帧距离仅 0.65px，天然贴合。

**弧形摆臂**：竿库 6 段中没有跑步/行走段，静持段 6 帧几乎一模一样。解决方案是用圆弧参数化生成握点轨迹：

```
θ(f) = θ0 · cos(2π(f-3)/6)     θ0 = 65°，R = 7
dx = R · sinθ        // 前后分量：正右/正左满幅 ±6，斜向 ±3~4，正上/下为 0
dy = -R · (1 - cosθ) // 抬落分量：弧两端抬高 4px，经过身侧最低 1px
```

帧号直接取身体 `FrameIndex % 6`，与步频严格同步；行走沿用同一条弧、幅度 ×0.4。峰值落在 f3（身体抬臂最高帧），因此竿的摆动与手臂抬落同相，不会脱手。

### 4.5 内观：羽化立绘走羽化库，持竿走竿帧

- **文件**：`PlayerObject.ResolveHumUpWeaponFrame`
- **改动**：手持鱼竿（Shape 49/50）时，用该竿自己的 `Image` 去羽化 `StateItem` 库取帧；空帧兜底回落固定仙兵帧。
- **覆盖范围**：自己的内观（`CharacterDialog`）与查看他人（`MainDialogs`）都经此函数，一处改动两边生效。
- **素材核对**：12 个羽化内观库（战/法/道/刺/弓/通用 × 男女）全部自带竿帧，无需新增素材。

### 4.6 属性：羽化重数与属性

- **配置**：`Configs\BuffSystem.ini` 新增 11 个非数字节名（`[羽化登仙]`、`[羽化一重]`…`[羽化十重]`），节名即枚举名，属"挂在已有枚举上"，**不占用 24 个自定义槽位**。
- **属性**：每重 攻击/魔法/道术 +5、防御/魔御 +3、生命/魔法 +100，十重封顶 +50/+30/+1000。
- **换重**：`SetHumUpStage` 先清旧标记与全部重数位再挂新位，避免属性叠加。

### 4.7 规则：未羽化禁穿 + 退回前必须脱装

1. **穿戴拦截**（`HumanObject.CanEquipItem`）：`!IsHumUp() && IsHumUpEquipShape(shape)` → 拒绝。英雄、假人自动穿戴走同一入口，一并覆盖。
2. **拒绝提示**（`PlayerObject.EquipItem`）：客户端收到 `Success = false` 只会静默解锁格子，因此服务端补一条提示「XX 蕴含仙灵之力，需羽化登仙后方可穿戴」。
3. **退回保护**（`SetHumUpStage` 改为返回 `bool`）：降到 0 重且身上仍有羽化装备时拒绝执行并提示「请先脱下身上的羽化专属装备，再退回羽化登仙」。NPC 脚本与 GM 命令均按返回值跳过成功文案，不会出现"提示退回成功但其实没退"。

### 4.8 武器职业判定：兼容 2000 段新编码

| 位置 | 旧逻辑 | 问题 | 新逻辑 |
|---|---|---|---|
| `Client.PlayerObject.HasClassWeapon` | `Weapon / 100` 判职业 | 2041/100 = 20 → 落 default（只认战法道）→ 刺客/弓箭被判"无本职业武器"，放技能弹「必须佩带适合的武器」 | Weapon ∈ 2001~2059 时走 `IsHumUpEquipShape` + `GetHumUpEquipClass`（十位 0 通用=全职业，其余须与自身职业一致） |
| `Server.HumanObject.RangeAttack` | `Shape / 100 != 2` 直接 return | 羽化弓 2051+ 静默射不出箭 | 兼容 `(shape - 2000) / 10 == 5` |

跨职业保护仍然有效：刺客佩戴战士羽化刃依旧被拦截。

### 4.9 BUFF 体系迁移（脱离自定义槽位）

**问题**：旧实现占用 11 个自定义槽位（Custom1 标记 + Custom3~12 重数），带来三个硬伤：

- 未知 `BuffType` 会让 `Buff(BinaryReader)` 抛异常 → 账号库回退 `.bak` → 服务器起不来；
- `ReloadBuffConfig` 会把 `IsCustom` 的 BUFF 直接从在线玩家身上移除（GM 重载一次即抹掉全服羽化）；
- 24 个自定义槽位被长期占掉 11 个。

**方案**：改用专用枚举 159~169，并做四层保障：

1. **硬注册**：`BuffInfo.Load` 内置 11 个类型（`Stack=Infinite`、`Visible=true`），不依赖 ini 是否写对。
2. **读档迁移**：`CharacterInfo.MigrateHumUpBuffs()` 在 Buff 循环后执行（覆盖英雄），**只改 `buff.Info` 指针，不 new 对象**——否则 `Stats / ExpireTime / Values / Data` 会丢失且登录重放补不回来。迁移幂等，并按类型去重。
3. **容错兜底**：`Buff(BinaryReader)` 对未注册类型 catch → 用 `BuffInfo.Unknown` 占位并置 `UnknownType`（`Type` 仍返回原始字节，存档可原样写回），只报一次日志。**这一条堵死了"一个字节让账号库回退"的路径。**
4. **兼容映射**：`BuffConfig.MapLegacyHumUp()` 把 `@GIVEBUFF 1`、`@GIVEBUFF 3~12` 及脚本里的槽位号翻译成新类型，避免挂出僵尸 BUFF；`GetSelectHumUpStage()` 同步识别新旧编码，保证选人界面立绘正确。

旧 ini 节 `[1]` / `[3]~[12]` **原样保留**，作为老存档的读档兼容层，代码不再写入。

### 4.10 命令体系

**NPC 脚本命令（本轮新增/补全）**

| 命令 | 位置 | 语法 | 说明 |
|---|---|---|---|
| `CHECKHUMUP` | #IF 条件 | `CHECKHUMUP` / `CHECKHUMUP n` / `CHECKHUMUP op n` | 无参=已登仙；`n`=重数 ≥ n；`op n`=显式比较 |

**GM 命令（已有，口径与 NPC 不同，勿混用）**

| 命令 | 行为 |
|---|---|
| `@HUMUP` / `@HUMUP 5` | 升一重 / **直接设为五重** |
