二、客户端：只显示 1 格内玩家

2.1 背景与目标

2 万假人进入视野后，客户端需要为每个角色绘制身体、武器、头、翅膀、坐骑、品质光效、名字、血条、伤害数字，以及其释放的技能特效。服务端虽然有可见数量上限（VisibleCap）限制单个真人能看见的假人数量，但客户端自身没有任何按距离或数量降级的逻辑——只要包发过来，就按满配角色全量渲染。

目标很明确：按距离丢弃绘制，但保留完整的游戏逻辑。看不见的人不需要画，也不应该被点到，否则免 shift 状态下点地面会变成原地打人。

2.2 显示规则

勾选后（内挂 → 其他 → 「只显示1格内玩家」），各类对象的行为如下表。

对象行为
自己始终显示
身边 1 格内的玩家（含 8 个斜向，切比雪夫距离 ≤ 1）显示
队友（组队名单内）任意距离常显
同会成员（双方行会名非空且相同）任意距离常显
鼠标指向的玩家常显
当前目标 / 魔法锁定 / 施法对象常显
其他远处玩家整条不画：身体、武器、头、翅膀、坐骑、品质光效、名字、对话气泡、血条、毒、伤害数字，以及其技能特效；同时不可点中
怪物 / NPC / 地面物品 / 宝宝 / 英雄不受影响

白名单的取舍理由：队友和同会看不见会直接打乱跑位与救人；目标看不见则锁定后凭空消失，反而不安全；鼠标指向的人若看不见，点人就没有任何反馈。

行会比对特意要求双方行会名非空——两个都没有行会的玩家不能因为都是空串就互相常显。

2.3 实现要点

唯一判定出口。所有绘制入口共用一个属性判定，避免出现"身体藏了名字还飘着"这类漏网：

代码示例

public bool NearPlayerFiltered

{

get

{

if (!Settings.NearPlayerOnly) return false;

if (User == null) return false;

if (!(this is PlayerObject) || this == User) return false;

if (this is HeroObject || this is UserHeroObject) return false;

if (NearPlayerKeepVisible) return false; // 常显白名单，必须在距离判定之前

 

return Math.Abs(Movement.X - User.Movement.X) > 1

|| Math.Abs(Movement.Y - User.Movement.Y) > 1;

}

}

闸门必须在方法第一句。六个绘制入口（Draw、DrawBehindEffects、DrawEffects、DrawBlend、DrawName、MouseOver）全部在方法体第一句返回，否则等于先完整画了一遍再丢弃，白费算力。这一点有专门的自动化断言守着。

世界层是缓存贴图。客户端世界层整屏渲染到 RenderTarget 并缓存，只调用场景重绘不会重画地图，用户会以为"勾了没反应"。因此勾选时同步把地图控件的贴图有效标记置为 false，强制重建。

2.6 取舍与已知副作用

鼠标扫过远处玩家会短暂闪现。因为鼠标指向属常显，扫到谁谁出现一帧。这是"看得到才点得到"的必要代价；若觉得扎眼，可以去掉鼠标指向常显，只保留目标、锁定、队友、行会。

远处队友会显示但怪物不会。这是刻意设计：怪物、掉落、NPC 是玩法必需，玩家不是。

该功能只省客户端绘制，服务端该发的包一个不少，带宽不变；真正的总量闸门仍是服务端可见数量上限，两者互补。

三、假人日志静音

3.1 三条通道与拦截点

服务端图形界面有两个文本框：「聊天日志」与「日志」。假人刷屏会同时污染这两处，2 万规模下会把界面拖死。

场景拦截位置做法
假人聊天 / 喊话 / 私聊PlayerObject.Chat 第一句全服唯一聊天日志写入点，前置「不是假人才写」判断
假人退出PlayerObject.StopGame退出原因写日志处同样包住；退出原因生成方法全服唯一调用点
假人登录FakePlayerManager.Login正常登录路径不写任何日志

3.2 本轮修复

复核时发现真正的刷屏点不在正常流程，而在失败路径：假人登录的两条日志——「上次对象未回收」与「创建失败」——位于每次重试都会执行的分支里。这个假人每秒重试一次、连败 5 次才报废，意味着单个坏假人能在 5 秒内连刷 5 条，2 万规模下很容易堆满日志。

改为限流：前 3 次照报（能看见问题），之后每 60 次报一条，并带上累计次数。

代码示例

rec.FailCount++;

if (rec.FailCount <= 3 || rec.FailCount % 60 == 0)

MessageQueue.Instance.Enqueue($"[假人] {rec.Name} 上次对象未回收（Info.Player 占用），跳过本次（第 {rec.FailCount} 次）");

3.3 验证结果

排雷工具 Tools/BotLogFilterTest 共 9 项，全部通过：

  • 聊天日志写入口全服只有 1 个，且被「假人排除」判断紧贴包住（中间夹了别的语句会报错）
  • 假人发言确实统一走统一聊天方法，AI 里没有直接写日志
  • 退出日志同样被紧贴包住；退出原因方法只有一个调用点
  • 登录方法里的失败日志全部限流
  • 假人管理器的日志一律带「假人」前缀，不冒充玩家上下线文案
  • 真人下线日志未被误伤（判断方向是「不是假人才写」）
  • 服务端产物比源码新

四、服务端内存治理

4.1 结构分析

在动手之前先算账。服务端内存的大头有三块：

大头规模估算说明
2 万假人档案约 100~300MB每个假人一份账号与角色档案；角色档案含 86 格背包、14 格装备、10 格交易、40 格任务、16 格精炼共 166 个物品槽，外加十多个列表
地图格数 × 约 40 字节地图格子用二维数组存储，但格子类型是类而非结构体，每格一个对象；总量取决于地图规模
GC 预留峰值的 30~50%运行时在分配峰值后默认不把空闲段还给系统，任务管理器看到的数字会明显高于存活对象

结论：能否压到 200MB，取决于测量结果，不能凭感觉改。

4.2 内存分布报告

新增开服内存报告，在开服完成（地图、物品库、假人档案均已就绪、网络未开）时打印一次，内容形如：

代码示例

──── 内存分布报告（开服完成）────

工作集 xxx MB｜私有内存 xxx MB｜托管堆 xxx MB｜提交内存 xxx MB（含 GC 预留）

地图 xx 张（xx 万格，格子是类对象，粗估 xx MB）｜怪物 xx 只（掉落表 xx 条）

物品库 xx｜技能库 xx｜任务 xx｜NPC xx（脚本 xx 个）｜行会 xx｜账号 xx｜角色 xx

假人档案 xx 个（每个 = 账号 + 角色档案 + 背包装备，粗估 xx MB）

报告只读不改，用于一次性定位"内存花在哪"。

4.3 定时全堆压缩

新增配置 [Memory] CompactMinutes（默认 0 表示关闭，钳制范围 0~1440 分钟）。大于 0 时，主循环每 N 分钟执行一次全堆压缩：

代码示例

System.Runtime.GCSettings.LargeObjectHeapCompactionMode =

System.Runtime.GCLargeObjectHeapCompactionMode.CompactOnce;

GC.Collect(2, GCCollectionMode.Forced, true, true);

压缩完成后日志会打前后差值，便于观察实际省下多少，例如：

代码示例

[内存] 已全堆压缩：托管堆 850→620 MB，提交内存 1100→760 MB

4.4 使用说明与风险

  • 建议值 30~60 分钟一次。压缩瞬间会有一次完整垃圾回收停顿（几十到几百毫秒），设得太密会影响手感。
  • 默认关闭，不改变现有服务器行为。
  • 配置文件必须在服务端停止状态下修改，否则关闭时回写会覆盖手工改动（该项目既有约定）。

4.5 下一步

拿到开服报告后再定方案：

  • 若大头在地图格子 → 方向是把格子类型结构体化或惰性化，工程量中等。
  • 若大头在假人档案 → 方向是"离线假人只保留轻量档案，背包装备上线时按需生成"，省得最多，但要兼顾角色保存逻辑，需要单独设计。
